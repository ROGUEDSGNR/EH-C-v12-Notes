# Hacking Web Servers Countermeasures

> #Web-Server-Attack-Countermeasures
	In previous sections, we covered the importance of a strong web server security posture, the risks associated with web server attacks, the typical attack methodologies, and the tools attackers use to exploit web servers. Now, we will focus on tools and techniques for securing web servers.
	
This section will discuss various methods for detecting web server attacks, implementing countermeasures, and employing defence strategies. Additionally, we will introduce commonly used security tools that help protect web servers from potential attacks. These tools perform tasks such as vulnerability scanning for both servers and web applications, sending alerts in case of hacking attempts, scanning for malware on the server, and conducting overall security assessments.

### Placing Web Servers in a Separate Secure Network Segment

1. **Segment the Network**: A secure web hosting network should be divided into at least three segments:
   - **Internet Segment**: The public-facing part of the network.
   - **Secure Server Segment (DMZ)**: Also known as the Demilitarized Zone, this segment is specifically for hosting web servers.
   - **Internal Network**: The private network for internal operations.

2. **Isolate the Web Server**: Place the web server in the **Server Security Segment (DMZ)**. This isolates it from both the public Internet and the internal network, reducing the risk of attacks spreading to other parts of the network.

3. **Use Firewalls for Protection**: Position firewalls to control traffic between the internal network, the DMZ, and the Internet. This setup filters incoming and outgoing traffic, providing an additional layer of security for the web server in the DMZ.

### Countermeasures: Patches and Updates

To maintain secure update and patch management for web servers, the following countermeasures should be implemented:

1. **Regular Vulnerability Scans and Updates**: Continuously scan for vulnerabilities, and patch and update server software regularly.

2. **Review Documentation**: Before applying any service pack, hotfix, or security patch, carefully read and peer review all related documentation.

3. **Apply Updates as Needed**: Deploy all updates as required, regardless of their type.

4. **Testing in Non-Production Environments**: Test service packs and hotfixes in a representative non-production environment before deploying them to production.

5. **Consistent Patch Levels**: Ensure that service packs, hotfixes, and security patches are uniformly applied across all domain controllers (DCs).

6. **Plan Server Outages and Backup**: Schedule server downtime for updates and ensure complete backups and emergency repair disks are available.

7. **Back-Out Plan**: Maintain a back-out plan to revert the system to its original state in case of a failed update.

8. **Periodic Service-Pack Upgrades**: Schedule regular service-pack upgrades to stay current, avoiding a backlog of more than two service packs.

9. **Disable Unused Script Extensions**: Disable any script extension mappings that are not actively in use.

10. **Avoid Default Configurations**: Avoid using default settings that come with web servers, which may pose security risks.

11. **Implement Virtual Patches**: Use virtual patches to provide additional logging and detection capabilities.

12. **Establish a Disaster Recovery Plan**: Develop a disaster recovery plan to address patch management failures.

13. **Conduct Risk Assessments**: Regularly assess risks to identify network segments that are most vulnerable or at high risk and prioritize them for patching.

14. **Inventory Endpoints and Dependencies**: Maintain an up-to-date inventory of all endpoints, services, and dependencies.

15. **Testing Before Full Deployment**: Ensure that all patches are thoroughly tested in a controlled environment before full system deployment.

16. **Deploy Patch Alerts**: Set up an alerting system for patch notifications to stay updated.

17. **Automate with Patch Management Tools**: Use tools like SolarWinds Patch Manager to automate patch management.

18. **Monitor and Report**: Regularly monitor and generate reports to confirm that patch management processes are working effectively.

19. **Limit Third-Party Risks**: Reduce exposure by minimizing the number of third-party software versions in use.

20. **Validate and Document Patches**: Validate and document all patch and update operations for easy access, analysis, and verification.

21. **Standardize Patch Management in SDLC**: Integrate a standardized patch management and security update methodology into the Software Development Life Cycle (SDLC).

### Countermeasures: Protocols and Accounts

To enhance security on web servers, consider the following protocol-related countermeasures:

1. **Block Unnecessary Ports and Protocols**: Disable all unused ports, ICMP traffic, and unnecessary protocols like NetBIOS and SMB.

2. **Harden TCP/IP Stack**: Strengthen the TCP/IP stack and ensure system software is always up-to-date with the latest patches and updates.

3. **Secure Insecure Protocols**: If protocols such as Telnet, POP3, SMTP, and FTP are in use, apply measures like IPsec policies to secure authentication and communication.

4. **Secure Remote Access**: For remote access, use tunneling and encryption protocols to ensure secure connections.

5. **Disable or Secure WebDAV**: If WebDAV is not required, disable it. If needed, secure it to prevent vulnerabilities.

6. **Use TLS/SSL**: Communicate with the web server using secure protocols like Transport Layer Security (TLS) or SSL.

7. **Isolate FTP Servers**: Ensure unidentified FTP servers operate in a directory tree separate from the web server's root.

8. **Configure HTTP Service Banners**: Mask host details such as OS type and version in the HTTP service banner to avoid revealing server information.

9. **Isolate Supporting Servers**: Place supporting servers (e.g., LDAP) outside the local subnet and filter traffic through a firewall.

10. **Use FTPS for File Transfers**: Ensure all file transfers through the web server use FTPS for secure data encryption.

#### Countermeasures for Securing Accounts

To protect user accounts on a web server, implement the following countermeasures:

1. **Remove Unused Modules**: Delete all unused modules and application extensions.

2. **Disable Default Accounts**: Turn off any default user accounts created during OS installation that are not needed.

3. **Set Minimum Permissions**: When creating a new web root directory, grant only the necessary NTFS permissions for anonymous IIS users to access web content.

4. **Limit Database Privileges**: Remove unnecessary database users and stored procedures, and enforce the principle of least privilege to defend against SQL injection.

5. **Use Secure Permissions**: Implement secure web permissions, NTFS permissions, and .NET Framework access controls, including URL authorization.

6. **Enforce Strong Password Policies**: Slow down brute-force and dictionary attacks with strong password requirements, and set up audits and alerts for failed login attempts.

7. **Use Least Privilege Accounts**: Run processes and services with the least privileged accounts whenever possible.

8. **Limit Admin Access**: Restrict administrator or root-level access to the fewest users necessary and keep records of such access.

9. **Maintain Encrypted Logs**: Store all user activity logs in an encrypted format, either on the server or on a secure intranet machine.

10. **Disable Non-Interactive Accounts**: Turn off any non-interactive accounts that don’t require an interactive login.

11. **Secure VPN Access**: Use secure VPNs like OpenVPN for multi-server or cross-server network access, allowing the use of a single account for multiple servers.

12. **Use Password Managers**: Implement tools like KeePass to manage password policies for multiple user accounts securely.

13. **Enable Separation of Duties (SoD)**: Configure the server to enforce separation of duties, reducing the risk of privilege misuse.

14. **Implement Password Expiry Policies**: Require periodic password changes to maintain account security.

15. **Enable Account Locking**: Set a limit on failed login attempts to lock accounts temporarily after multiple failures.

16. **Enable 2FA/MFA**: Add an extra layer of security for user accounts with two-factor or multi-factor authentication (2FA/MFA).

### Countermeasures: Files and Directories

To secure files and directories on a web server, consider implementing the following countermeasures:

1. **Remove Unnecessary Files in .jar Files**: Eliminate any extraneous files within `.jar` archives to reduce potential attack surfaces.

2. **Protect Sensitive Configuration in Bytecode**: Avoid embedding sensitive configuration details in bytecode to prevent exposure.

3. **Avoid Mapping Virtual Directories Across Servers**: Refrain from mapping virtual directories between different servers or across networks to minimize risk.

4. **Regularly Monitor Logs**: Frequently review network service logs, website access logs, database server logs (e.g., Microsoft SQL Server, MySQL, Oracle), and OS logs to detect unusual activity.

5. **Disable Directory Listings**: Prevent the server from listing directory contents to avoid exposing files to unauthorized users.

6. **Remove Non-Web Files**: Delete unnecessary files such as archives, backups, text files, and header/include files from web directories.

7. **Restrict Certain File Types**: Use a resource map to prevent the server from serving specific file types that are not needed for web applications.

8. **Separate Web Application Files from System Files**: Store web application files and scripts on a separate partition or drive from the OS, logs, and system files for added security.

9. **Use a Sandbox for the Web Server**: Run the web server within a sandboxed directory to prevent access to system files.

10. **Prevent Non-Web Files from Being Referenced in URLs**: Ensure only web-related files are accessible via URLs to reduce exposure to non-web files.

11. **Run with Least Privileges**: Configure web server processes to operate with minimal privileges, granting access only to required directories.

12. **Filter Out Meta Characters in User Inputs**: Exclude meta characters from user inputs to ensure secure input handling and prevent command injection.

13. **Use File Integrity Checkers**: Implement file integrity checkers to monitor and verify the integrity of web content and detect intrusions.

### Detecting Web Server Hacking Attempts

To identify hacking attempts on a web server, you can use a **Website Change Detection System**, which performs the following tasks:

1. **Running Detection Scripts**: Executes specific scripts on the server to monitor and detect any changes made to existing executable files or new files added to the server.

2. **Comparing Hash Values**: Regularly checks the hash values of files on the server against a master hash to identify any unauthorized changes in the codebase.

3. **User Alerts**: Sends alerts to the user whenever a change is detected on the server, allowing immediate action.

**Example Tool**: 
- **DirectoryMonitor** is an automated tool that scans web folders for any changes in the codebase and sends email alerts if modifications are detected. 

### How to Defend Against Web Server Attacks

#### 1. Ports
- Regularly monitor all ports on the web server to prevent unnecessary traffic, which can increase vulnerability to malware.
- Limit public access to port 80 (HTTP) and port 443 (HTTPS). If port 80 remains open, the server may be vulnerable to DoS attacks, which consume resources.
- Encrypt or restrict intranet traffic to secure the web server.
- Use IP address filtering, such as "deny this IP address" rules or "routed blackhole" commands, to block spoofed IP addresses and defend against attacks.

#### 2. Server Certificates
- Server certificates provide security by verifying server identity and are signed by trusted authorities. However, attackers can use forged certificates to perform Man-in-the-Middle (MITM) attacks.
- Techniques to prevent MITM attacks include:
  - Direct validation of certificates.
  - Using protocols that do not rely on third-party certificate validation.
  - Allowing domains to verify their certificates with previously established user credentials.
  - Applying robust cryptographic techniques for enhanced server identity validation.
  - Ensuring certificate data ranges are valid and certificates are used correctly.
  - Verifying that certificates are not revoked and trace back to a trusted root authority.

#### 3. Machine.config
The `machine.config` file secures information by setting machine-level configurations for the .NET framework. Key measures include:
- Map protected resources to `HttpForbiddenHandler` and remove unused `HttpModules`.
- Disable tracing (`<trace enable="false"/>`) and turn off debug compilations.
- Ensure ASP.NET errors are not returned to the client.
- Verify session state settings to prevent unauthorized access.

#### 4. Code Access Security
To ensure secure code access on the web server:
- Implement secure coding practices to prevent source code disclosure and input validation attacks.
- Restrict code access policy settings to prevent execution of untrusted code from the Internet or intranet.
- Configure IIS to reject URLs with `../` to prevent path traversal attacks, restrict access to system commands, and keep ACLs tight.
- Regularly apply patches and updates to prevent security vulnerabilities.

### Additional Defense Measures

#### Access Control
1. **Apply Restricted ACLs** and block remote registry access.
2. **Secure the SAM** (for stand-alone servers).
3. Configure **NTFS permissions** for key security files and the metabase.
4. **Remove unnecessary ISAPI filters**.

#### File and Directory Security
5. Relocate sites and directories to **non-system partitions**.
6. Remove **IIS script mappings** for unnecessary file types.
7. Set up **audit logging** for tracking access to log files.

#### Physical and Network Security
8. Use a **dedicated machine** as the web server.
9. **Create URL mappings** to internal servers with caution.
10. **Do not install IIS** on a domain controller.
11. Use **session ID tracking** for connections.
12. Install the database server (e.g., SQL Server) on a **separate server**.
13. Employ security tools and **automated scanners**.

#### General Security Practices
14. Physically protect the server in a secure machine room.
15. **Do not connect IIS** to the Internet until fully hardened.
16. Limit **local login access** to administrators only.
17. Use a **separate anonymous account** for each application.
18. Limit server functions to essential web technologies.
19. **Screen and filter** incoming traffic requests.

### Additional Measures to Defend Against Web Server Attacks

1. **Access Control**:
   - Apply restricted ACLs and block remote registry administration.
   - Secure the SAM file on stand-alone servers.

2. **File and Directory Security**:
   - Configure security-related settings properly and secure the metabase file with hardened NTFS permissions.
   - Remove unnecessary ISAPI filters from the server.
   - Remove all unnecessary file shares, including default administration shares, and secure the remaining shares with restricted NTFS permissions.
   - Move websites and virtual directories to non-system partitions, using IIS permissions to limit access.
   - Remove unnecessary IIS script mappings for optional file extensions to prevent exploits in ISAPI extensions.
   - Enable a minimum level of auditing on the server and use NTFS permissions to secure log files.

3. **Network and Physical Security**:
   - Use a dedicated machine for the web server.
   - Create URL mappings to internal servers with caution.
   - Avoid installing IIS on a domain controller.
   - Use server-side session ID tracking, matching connections with timestamps, IP addresses, and other identifiers.
   - Install the database server, such as Microsoft SQL Server, on a separate machine if used as a backend.

4. **Server Configuration and Hardening**:
   - Use security tools and automated scanners provided with the web server software.
   - Physically secure the web server in a protected machine room.
   - Do not connect IIS to the Internet until it has been fully hardened.
   - Limit local login access to the administrator only.
   - Configure a separate anonymous user account for each hosted application.
   - Restrict server functionality to only necessary web technologies.
   - Screen and filter all incoming traffic.

5. **Storage and Anti-Bot Protection**:
   - Store website files and scripts on a separate partition or drive from system files.
   - Use an anti-bot service like DataDome for real-time detection of botnets.

### Defending Against HTTP Response Splitting and Web Cache Poisoning

To prevent HTTP response splitting and web cache poisoning attacks, follow these guidelines:

1. **Cookie Handling**:
   - Remove carriage returns (CRs) and linefeeds (LFs) from data before setting it in an HTTP response header.
   - Use third-party tools to identify and patch security vulnerabilities, particularly to defend against CRLF injection.
   - Ensure that application engines are always up to date.

2. **UDP Source Port Randomization**:
   - Utilize UDP source port randomization to protect servers from blind response forgery attacks.
   - Limit the number of simultaneous recursive queries and increase the time-to-live (TTL) for legitimate records to reduce exposure.

### Additional Defense Measures by Role

#### For Server Administrators
   - Use the latest version of web server software.
   - Regularly update and patch the OS and web server software.
   - Run web vulnerability scanners frequently to identify and address security issues.

#### For Application Developers
   - Limit the web application's access to specific IP addresses.
   - Disallow the use of CR (`%0d` or `\r`) and LF (`%0a` or `\n`) characters in HTTP headers.
   - Follow HTTP/1.1 specifications as outlined in RFC 2616.
   - Parse and sanitize all user inputs and other encoded data before including them in HTTP headers.

#### For Proxy Servers
   - Avoid sharing incoming TCP connections among different clients.
   - Use separate TCP connections for each virtual host handled by the proxy.
   - Correctly implement "maintain request host header" to ensure accurate request handling.

### How to Defend Against DNS Hijacking

To protect against DNS hijacking, consider implementing the following strategies:

1. **Choose a Trusted Registrar**: Select an ICANN-accredited registrar and enable the **REGISTRAR-LOCK** feature on your domain name for added security.

2. **Secure Registrant Account Information**: Keep account details safe to prevent unauthorized changes to DNS records.

3. **Include DNS Hijacking in Incident Response Planning**: Address DNS hijacking in your organization’s incident response and business continuity plans.

4. **Use DNS Monitoring Tools**: Employ DNS monitoring services to track the IP address of your DNS server and receive alerts for unusual changes.

5. **Avoid Untrusted Downloads**: Do not download audio/video codecs or other software from unreliable websites.

6. **Install and Update Antivirus Software**: Regularly update antivirus programs to detect and prevent malware that can manipulate DNS settings.

7. **Change Default Router Passwords**: Replace the default router password with a strong, unique one to prevent unauthorized access.

8. **Restrict Zone Transfers**: Limit DNS zone transfers and use script-blocking browser extensions to minimize exposure to potential attacks.

9. **Implement DNSSEC**: Enable Domain Name System Security Extensions (DNSSEC) to add an extra security layer, preventing DNS manipulation.

10. **Enforce Strong Password Policies**: Use strong, unique passwords and follow strict user management practices to secure access to DNS configurations.

11. **Choose DNS Providers with Strong SLAs**: When selecting a DNS provider, ensure they offer robust service-level agreements (SLAs) that include reliable support and a hardened infrastructure against attacks.

12. **Use Master-Slave DNS Configuration**: Configure a **master-slave DNS setup** where the master server has no Internet access, with two slave servers that only update from the master, reducing risk if a slave is compromised.

13. **Constant DNS Server Monitoring**: Continuously monitor DNS servers to ensure they return the correct IP addresses and detect any unauthorized changes promptly.

14. **Secure Router Settings**: Regularly change the router’s default username and password, and keep the firmware up-to-date to defend against new vulnerabilities.

15. **Use a VPN for Secure Communication**: Employ a virtual private network (VPN) with encrypted tunnels to protect data from eavesdropping and unauthorized access during Internet communication.

16. **Utilize Firewall Protection**: Use firewall services to secure original DNS resolvers and filter out rogue DNS resolver traffic.

17. **Implement Strong Access Controls**: Use multi-factor authentication (MFA) and hardware security devices to restrict access to the DNS server.

18. **Install Script Blockers**: Add script-blocking extensions in browsers to prevent malicious scripts that may alter DNS settings.

19. **Avoid Free VPN Services**: Use only secure and reputable VPN services, as free VPNs may track and record your activities.

### Patches and Hotfixes

1. **Hotfixes**: 
   - Hotfixes are specific updates intended to resolve particular customer issues. They are often limited in distribution and may not be available outside the customer organization.

2. **Patches**: 
   - A patch is a small software update designed to address problems, security vulnerabilities, and bugs, enhancing the performance of a program or its data.

3. **User Notifications**:
   - Users may receive notifications about patches or hotfixes through emails or the vendor's website.

4. **Purpose of Patches**:
   - Patches can be viewed as repair jobs that address programming issues in software.

5. **Combined Hotfixes**:
   - Hotfixes may sometimes be bundled together as a **combined hotfix** or **service pack**, delivering multiple fixes in one package. 

### What is Patch Management?

**Patch management** is the process of fixing known vulnerabilities by ensuring that the appropriate patches are installed on a system.

### Automated Patch Management Process

1. **Detect**:
   - Use tools to identify missing security patches on the system.

2. **Assess**:
   - Evaluate the issues and the associated severity to understand the potential impact and decide on the patching priority.

3. **Acquire**:
   - Download the required patch for testing purposes.

4. **Test**:
   - Install the patch on a testing machine first to verify its effects and ensure it does not disrupt the system.

5. **Deploy**:
   - Roll out the patch to production systems, ensuring that applications are unaffected and continue to operate as expected.

6. **Maintain**:
   - Subscribe to notifications for newly detected vulnerabilities to stay informed and act promptly.

### Installing a Patch

Users can access and install security patches through the World Wide Web. Patches can be installed in two main ways:

1. **Manual Installation**:
   - In this method, the user downloads the patch directly from the vendor’s website and manually installs it.

2. **Automatic Installation**:
   - In this method, applications use an **Auto Update** feature to download and install updates automatically.

---

### Key Steps for Installing and Verifying a Security Patch

1. **Identify Trusted Sources for Updates and Patches**:
   - It is crucial to obtain patches from trusted sources, as unverified patches can introduce vulnerabilities rather than improve security.
   - Methods to ensure appropriate sources:
     - Develop a **patch management plan** that aligns with business goals and operational needs.
     - Download updates and patches from the official websites of application or OS vendors.
     - Register on vendor websites to receive alerts and notifications about new patches and updates.

2. **Verify Patches Before Installation**:
   - Always verify the patch source before installing it to ensure authenticity.
   - Use a patch management program to confirm file versions and checksums, ensuring the patch is legitimate and unaltered.

3. **Monitor Patched Systems**:
   - Ensure that the patch management tool can monitor systems after patch deployment to check for successful installation and functionality.
   - The patch management team should routinely check for new updates and patches to maintain system security.
